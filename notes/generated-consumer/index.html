GRAPHQL / GENERATED CONSUMERS

검사는 통과했지만, 생성 타입은 예전 것이었다The checks passed. The generated types were stale.

쿼리는 후보 스키마로 검증했습니다. 생성 타입을 사용하는 코드(consumer)는 이전 스키마의 타입으로 컴파일했습니다. 둘 다 통과했지만, 같은 계약을 검사한 것은 아니었습니다.

Query validation used the candidate schema. Consumer compilation used baseline generated types. Both passed, but they did not check the same contract.

01두 검사에 들어간 입력The inputs behind two passing checks

개인 Apollo Federation 실험에서 name을 nullable로 바꿨습니다. 두 쿼리는 여전히 유효했지만, 스키마 비교에서는 non-null 보장 약화를 breaking으로 분류했습니다. 여기서 통과한 것은 쿼리 검증과 이전 타입에 대한 컴파일입니다.

In a personal Apollo Federation lab, I made name nullable. Both queries remained valid, while schema comparison classified the weakened non-null guarantee as breaking. The two passing checks were query validation and compilation against stale types.

이전 생성 타입의 name은 여전히 string이었습니다. 따라서 컴파일 성공은 새 계약을 처리한다는 근거가 아니었습니다. 새 계약이 컴파일 입력에 반영되지 않은 상태였습니다.

The old generated type still declared name as string. A passing compile did not establish that the code handled the new contract: that contract had not reached the compiler input.

두 통과 결과를 묶기 전에, 같은 변경을 검사했는지 확인해야 합니다.Before combining two passing results, check that they cover the same change.

02재생성·정책·선택 필드를 따로 비교하기Separate freshness, policy and selected fields

상품명 함수의 return product.name.toUpperCase();는 그대로 두었습니다. 공식 Codegen으로 타입을 다시 만들자 실제 TypeScript 컴파일 결과가 달라졌습니다.

The name function kept the same return product.name.toUpperCase();. Regenerating its types with official Codegen changed the real TypeScript compilation result.

생성 정책도 별도 변수였습니다. futureProofEnums: true는 enum 유니온에 "%future added value"를 추가합니다. 스키마를 바꾸지 않아도 assertNever를 쓰는 재고 상태 함수는 컴파일에 실패했고, 대체 문구를 반환하는 함수는 통과했습니다. 이 설정이 런타임 응답을 변환해 주는 것은 아닙니다.

Generation policy was a separate variable. futureProofEnums: true adds "%future added value" to the enum union. Even without a schema change, the stock function using assertNever failed to compile; the fallback function passed. The setting does not transform runtime responses.

반대로, 쿼리가 선택하지 않는 nullable 필드를 추가하면 스키마 해시가 달라져도 두 생성 타입 파일의 바이트는 같았습니다. 해시 차이는 입력 차이의 근거이지, 곧바로 breaking 판정은 아닙니다.

Adding an unselected nullable field changed the schema hash but left both generated type files byte-identical. A different hash establishes different input, not automatically a breaking change.

03직접 확인할 수 있는 근거Evidence you can inspect

전체 실행은 8개 조건, 실제 컴파일 28회이며, 이 글은 주요 대조군을 골라 설명합니다. 코드·쿼리·스키마는 개인 실험용입니다. 리졸버와 예제 함수는 실행하지 않았으며, 회사나 실서비스의 성과를 주장하지 않습니다.

The full run contains 8 cases and 28 actual compilations; this note presents selected controls. Code, queries and schemas are synthetic personal fixtures. Resolvers and consumer functions were not executed; these are not employer or production results.
