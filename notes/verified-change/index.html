VERIFIED CHANGE / DEVELOPER AUTOMATION

‘통과’의 의미까지 검증하기Verify what “passed” means.

자동화가 만든 패치는 코드와 검사 설정을 함께 바꿀 수 있습니다. 승인하기 전에, 통과 결과가 어떤 코드와 어떤 기준에 해당하는지 확인해야 합니다.

An automated patch can change both the code and its checking configuration. Before approval, a green result needs to identify the code examined and the rules applied.

01컴파일러는 설정대로 통과시켰다The compiler passed what it was told to check

암묵적 any 매개변수가 두 개 있는 코드를 검사했지만, TypeScript 프로세스는 오류를 보고하지 않고 종료했습니다. 설정에는 여전히 strict: true가 있었습니다.

스크립트로 준비한 동일한 변경안을 두 개의 컴파일러 프로세스로 검사했습니다. LLM을 호출한 실험은 아닙니다. 후보의 설정을 읽은 비교용 검사기는 종료 코드 0을 반환했습니다. 별도로 정한 strict 옵션과 정확한 파일 목록을 쓰는 검사기는 오류 두 개를 찾아 종료 코드 2를 반환했고, 승인은 거부됐습니다. 런타임 동작을 확인하는 다섯 개 검증 항목은 모두 통과했습니다.

A real TypeScript process returned zero diagnostics for code with two implicit-any parameters. Its configuration still said strict: true.

I checked the same scripted candidate in two separate compiler processes. No LLM is called. The comparison checker read the candidate’s configuration and exited 0. The trusted checker supplied its own strict options and exact source-file list. It found both errors, exited 2, and approval was refused. All five runtime assertions still passed.

src/retry-policy.ts

export function mayRetry(method, status) {
  return (method === 'GET' || method === 'HEAD') &&
    (status === 429 || (status >= 500 && status <= 599));
}

tsconfig.json — 후보가 정한 옵션candidate-controlled options 

{ "compilerOptions": { "strict": true, "noCheck": true } }

noCheck는 전체 타입 검사를 생략하는 옵션입니다. 컴파일러는 설정대로 동작했습니다. 문제는 검사 대상에 포함된 설정으로 필수 타입 검사의 범위까지 바꿀 수 있었다는 점입니다. TypeScript 공식 문서.

검사 옵션과 파일 목록을 별도로 정하면 이 예시의 tsconfig 경로는 막을 수 있습니다. 다만 TypeScript는 // @ts-nocheck 같은 소스 수준의 지시문을 계속 따릅니다. 현재 정책은 이를 금지하지 않습니다. 소스의 검사 생략 지시문까지 제한하려면, 이를 허용할 조건과 검토 절차를 별도로 정해야 합니다. 소스 지시문에 대한 공식 문서.

noCheck disables full type checking. The compiler was following its configuration. The required type check used a configuration the patch could change. TypeScript documentation.

Fixed options and a fixed file list close the candidate-configuration route shown here. TypeScript still honors source-level directives such as // @ts-nocheck, which this policy allows. Restricting those suppressions needs an explicit additional rule and review boundary. TypeScript source-directive documentation.

02산출물과 통과 기준을 함께 고정하기Bind both the artifact and the acceptance policy

비교용 결과는 승인 근거로 받지 않습니다. 승인 계층은 결과 보고서와 별개로 필수 검사 목록을 알고 있으며, 프로세스가 성공해도 결과가 비어 있으면 거부합니다. 필수 검사가 모두 실행됐는지와, 각 검사가 요구한 내용을 실제로 확인했는지를 따로 검사해야 합니다.

검사한 코드와 실제로 반영할 코드도 같아야 합니다. 다른 실행 사례에서는 커밋 A를 검사한 뒤 작업 파일을 수정하고, 현재 작업 공간을 새로 커밋해 선택했습니다. 사후 동작 검사가 실패했습니다. 보호된 경로는 이미 검증한 커밋을 선택했고, 수정된 작업 공간은 그대로 남겼습니다. Git ref 변경은 체크아웃 갱신과 다릅니다.

  • 불변 커밋의 스냅샷을 검사하고, 검사 옵션과 필수 파일·검사 목록을 후보의 통제 밖에 둡니다.
  • 유효 기간이 남은 검사 결과를 후보, 검사 실행, 검증 정책에 연결하고 검사기·제어 코드의 해시와 명시된 도구 버전을 기록합니다.
  • 승인을 기준 커밋, 후보, 근거 다이제스트에 연결하고 조건부 ref 변경 직전에 재확인합니다.

Git의 old-value 인수는 현재 ref가 승인된 기준을 가리킬 때만 변경하도록 합니다. 기록된 두 프로세스의 경합에서는 한 번의 변경만 성공했습니다. 후보나 신뢰하는 정책이 바뀌면 다시 검증하고 검토해야 합니다. 필요한 정책 변경에는 별도의 검토 경계가 있어야 합니다.

The comparison result is excluded from acceptable evidence. The approval layer knows the required check inventory independently and rejects an empty result even when the process exits successfully. Completeness and stable check meaning are both required.

The code’s identity must survive, too. In another recorded case, the workflow checked commit A, edited the workspace, then committed and selected that workspace. A later runtime check failed. The protected path selected the already-verified commit and left the edited workspace alone. Updating a Git ref does not update a checkout.

  • Verify snapshots of an immutable commit. Keep checker options and required source/check inventories outside the candidate’s control.
  • Bind fresh results to the candidate, checker invocation and verification policy. Record checker/control-source hashes and declared tool versions.
  • Bind approval to the expected base, candidate and evidence digest. Revalidate before the conditional ref update.

Git’s old-value argument allows the update only while the ref still points to the approved base. In the recorded two-process race, one update succeeded. Changing the candidate or trusted policy costs another verification and review. A legitimate policy change needs its own review boundary.

03현재 값이 말해주지 않는 것What the current value cannot tell us

Git이 변경을 수락한 직후, 응답을 남기기 전에 실행 프로세스를 종료했습니다. 재조회는 현재 ref를 알려주지만 누가 바꿨는지는 입증하지 않습니다. 별도의 A→B→A 회귀 검사에서는 기준으로 되돌린 뒤 아직 유효한 승인을 재사용하자 변경이 다시 성공했습니다. 이 회귀 검사는 아래 다섯 사례의 저장 보고서와 구분됩니다. 현재 ref 값이 같아도, 그 사이 다른 값으로 바뀌었다가 돌아왔는지는 알 수 없습니다.

가상 코드, 실제 로컬 Git·컴파일러 프로세스, 스크립트로 입력한 승인을 사용했고 LLM은 호출하지 않았습니다. 기록은 서명하지 않았으며 로컬 실행 환경을 신뢰합니다. 승인자의 신원 인증이나 악의적 코드 격리, 배포, 외부 동작의 정확히 한 번 실행을 보장하지 않습니다. 변경 대상은 로컬 ref 하나입니다.

The executor was terminated after Git accepted an update but before acknowledgement. Reconciliation observes the current ref; it cannot establish who changed it. A separate A→B→A regression restored the base and successfully reused the same still-fresh approval. That regression is distinct from the five-case saved report linked below. A current-value comparison has no memory of prior transitions.

These runs use synthetic code, real local Git/compiler processes and scripted approvals. They use no LLM. The records are unsigned and the local runner is trusted. This does not authenticate a reviewer, isolate hostile code, deploy software or establish exactly-once external execution. The write changes one local ref.

승인하려면 어떤 커밋을 어떤 기준으로 검사했는지, 그 결과를 지금 반영할 변경에 써도 되는지 확인해야 합니다.
“Passed” should identify a precise proposition: this artifact satisfied these checks, under this policy, for this permitted transition.
