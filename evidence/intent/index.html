응답의 실패와 예약의 실패는 다릅니다. A lost response. Not necessarily a lost reservation.

같은 통신 실패 뒤, 어떤 요청을 다시 보내느냐가 결과를 바꿉니다. 실제 HTTP와 SQLite로 차이를 재현했습니다. After the same transport failure, the identity of the retry changes the result. Real HTTP requests and SQLite records make the distinction observable.

이 기록을 읽기 전에

예약 버튼을 눌렀는데 응답이 끊겼습니다. 서버에는 이미 예약이 저장됐을 수 있습니다. 여기서 새 요청을 만들면 어떤 일이 생길까요?

실제 HTTP와 SQLite를 쓰는 개인 실험입니다. 같은 예약 시도를 식별하는 키를 유지한 경우와 새 키로 보낸 경우를 비교합니다. 아래의 예약 건수부터 보고, 각 사례를 펼치면 요청·응답을 확인할 수 있습니다.

Before reading the capture

A reservation response disappears. The server may already have saved the reservation. What happens if the retry creates a new request?

This independent HTTP/SQLite experiment compares keeping the key that identifies one reservation attempt with sending a fresh key. Start with the reservation counts below; expand a case to inspect its requests and responses.
